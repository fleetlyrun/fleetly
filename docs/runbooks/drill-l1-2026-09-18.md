- 演练日期：2026-09-19 01:52 UTC（容器内时钟；票面日期 2026-09-18）
- 环境：docker:29.8.1-dind 特权容器（干净状态，单节点 Swarm），fleetlyd
  版本 v0.1.0-uga（交叉编译，`CGO_ENABLED=0`），SQLite（modernc，WAL）
- 手册依据：[backup-restore.md](backup-restore.md) §4（恢复顺序）/§5（验证清单）
- 执行形态：步骤按手册逐条脚本化执行（等价于人工命令序列；命令清单见 §3）
- 结论：**PASS —— 恢复流程实测 3 秒完成（预算 ≤10 分钟，600 秒）**；
  灾前台账行、应用行、密钥指纹核对全部通过，恢复后备份链重新闭环。

## 1. 演练场景

1. 安装 + 启动 daemon（boot 即产生一条 `daily` 备份，verified）；
2. 制造可验证状态：入队一个 `drillapp` 部署（应用行落库）；
3. 手动触发一次 `manual` 备份（同步等待 `verify=verified`）——即「灾前
   最后一次备份」；
4. **模拟灾难**：停 daemon → 删除 `fleetly.db`（连同 `-wal`/`-shm`）；
5. 按 runbook §4 执行恢复（校验备份集 → 抄底 → 回填 → 启动）；
6. 按 runbook §5 执行验证清单。

## 4. 快照时点语义注记（如实记录）

灾前最后一次备份（manual，`01M2VNTFGX0191M22WRRNH7EN8`）的**台账行不会
出现在它自己的快照里**——快照是 `VACUUM INTO` 时点的库事实，该行在快照
之后才落账。因此恢复后核对「灾前状态」用的是快照时点已存在的证据：boot
`daily` 行与应用行；两者均在恢复后的台账/应用清单中复现。

## 5. 首次配置耗时

首次（含阅读手册与脚本化）配置耗时 5 秒（setup_seconds=5，不计入恢复预
算）；纯恢复流程 3 秒。运维首次按手册人工执行（非脚本）预计 <2 分钟——
全部命令见 [backup-restore.md](backup-restore.md) §4，逐条可直接复制执行。

## 6. 不覆盖项（如实声明）

- 本演练为 **L1**（同机、raft 无损、只回填 SQLite）。L2（新集群 + 人工
  rebind）演练按 scope-freeze 属 v0.2 正式演练项。
- Engine/主机冷备轨不在本演练（见 upgrade.md §3；有状态应用停机语义）。
- 异机恢复（备份介质搬运）未覆盖——v0.1 备份目录在本机，异机上传随 v0.2
  S3 目标。
