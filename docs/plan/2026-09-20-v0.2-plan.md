## 1. 定位与红线

**v0.2 主题 = 「投产」**：把 v0.1 的单机可用推进到目标画像的生产基线（2 节点）+ 托管数据 + 基本可观测，并清偿 v0.1 发布检查单欠账（真 VPS dogfooding）。

横切红线（全程生效，违反即范围违规）：

1. **资源预算**：平台组件 idle 总量 <400MB（含 containerd ≈44-50MB，FZ-9 口径）；任何 Epic 引入新常驻组件前先测预算——**禁止 fluentd/Loki/Grafana/Temporal 级重依赖**（调研 A1：zane-ops 控制面 10 容器 ≈7GB limit 是镜鉴，同类需求我们有轻路径）。
2. **轻单核不变**：fleetlyd 单进程单写点（SQLite）不引入外部状态库/编排引擎；多写点需求出现时先走裁决轮（调研 R6 仅作备用记录）。
3. **契约纪律沿用**：错误码/事件只增 + 评审；注册表码集设计全量、实现按需消费；proto breaking 门禁；Console 锚点（data-testid 清单）不破坏。
4. **文档先行**：每个 Epic 启动实现前补/更新专项设计文档并过裁决轮——v0.1 的冻结清单模式（FZ 编号）延续为 **V2 编号**。

**与架构 §4.3 排序的唯一偏差**：路线图原排序「多节点首项」，本规划把 W1 dogfooding 提到 W2 多节点之前——理由：①E8 是 v0.1 发布检查单明文欠账（检查单勾完时点 = M2）；②我们自己先当一次「v0.1 投产用户」，E1 的验收演练（2 节点）直接复用这条真 VPS 路径；③E1 体量大、设计前置长，W0 裁决轮启动其设计不损失墙钟。**该偏差提交 D-V2-1 裁决**，若否决则 W1/W2 互换。

## 7. 借鉴与避坑红线（源自 [zane-ops 对照调研](../research/2026-09-20-zane-ops-comparison.md)）

- **直接进票的借鉴**：R1→E7 细则（§5）；R2→T0-V2.2；R3→T0-V2.4；R4→E6（D-V2-5）；R5→E4/FZ-1；R7→T0-V2.3；R6 仅记录备用；R8（PR 预览先例）→v0.3 参考。
- **避坑红线**：A1 重生态依赖（§1 红线 1/2）；A2 on-demand TLS 不学（保持台账先行 + 集中签发）；A3 日志保持 SSE 不退轮询；A4 compose 校验保持自研白名单 + golden（不引入 `docker compose config` 子进程）；A5 webshell 超时/审计随 R1 落；A6 可变镜像引用（R7 门禁化）。

## 8. v0.2 明确不做（范围外）

多用户/RBAC/审计留存（v0.3+，商业候选）；PR 预览环境与官方模板目录（v0.3）；内置/打包 S3（触发式，D4）；通配符证书与 DNS-01（v0.3 按服务商）；`depends_on`/`extends`/外部网络/`network_mode: host` 开放（v0.3 受控扩展）；多 manager/多写点与自研 node 协议（Swarm 承担，D2/D12）；节点生命周期 API（用 `docker node` + 文档/UI 指引，D18）；通用工作流引擎（Temporal 类，A1）；Compose 全量语义支持。

## 9. 执行纪律（沿用 v0.1）

只从 frontier 取票（§4 表为初始 frontier，W2+ 启动前细化）；票据完成定义 = 验收全勾 + 设计文档章节未偏离；发现设计缺口停下补设计（裁决轮），不允许票据内私改语义；每波次收口跑文档↔实现一致性抽查并回填本表状态；还原点提交 + 阶段验收门沿用 subagent-sequential-implement 纪律。
